# Requirements Document

## Introduction

Arabclue (أراب كلاو) is a bilingual Arabic/English B2B SaaS platform that prepares compliant technical and financial proposal **structure** for Saudi government tenders on Etimad. The platform already ships a large working surface: 99 API route handlers, 18 public and application pages, 51 Prisma models, a five-stage agent pipeline, a bilingual document engine with HTML/PDF/PPTX writers, a validation gate that blocks export on pricing language and placeholders, and MyFatoorah webhook verification.

This specification covers the remaining work required to make the platform production-complete. Scope was derived from evidence in the repository rather than inline markers (the source tree contains no `TODO`, `FIXME`, or `placeholder` markers). The evidence classes were:

1. **Dead data models** — Prisma models that no application code reads or writes.
2. **Write-side gaps** — models that application code reads but nothing populates.
3. **Unreachable server capability** — route handlers and library functions with no caller.
4. **Explicit non-implementation** — code paths that raise a documented "not implemented" error while a product document promises the capability.
5. **Broken user journeys** — flows whose entry point does not exist.

Concrete findings that define this scope:

| Finding | Evidence |
| --- | --- |
| No self-serve account creation, no account recovery, no email verification | No registration/reset/verification route handler, page, or Prisma model exists; `src/app/api/workspaces/route.ts:129` rejects invitees who have no account |
| Analytics dashboard can never show data | `db.analyticsEvent` is read in `src/app/api/analytics/proposals/route.ts:78` and `:95` and written nowhere |
| Standard clause library is a dead model | `StandardClause` (`prisma/schema.prisma:1155`) has zero references in `src/**` |
| No contract template authoring or template version history | `db.contractTemplate` / `db.contractTemplateVersion` are only upserted as a catalog mirror in `src/lib/contract-template-persistence.ts:1001,1021`; `GET /api/contracts/templates` exposes no write method |
| Structured XLSX export raises a capability error | `src/lib/proposal-layout-export.ts:1199-1218`, while `prd/PRD.md` §4.5 promises `PDF / PPTX / XLSX / ZIP` |
| Recurring subscription billing never activates | `createRecurringPayment` (`src/lib/myfatoorah.ts:372`) has no caller; `MyFatoorahRecurringProfile` rows are only ever updated (`src/app/api/billing/webhook/route.ts:115`), never created |
| Knowledge approval queue API has no consumer | `GET /api/knowledge/pending-approval` has no client caller; `knowledge-review-controls.tsx` reads `/api/documents` and `/api/workspaces` only |
| Payment reconciliation is not operator-reachable | `GET,POST /api/admin/billing/reconcile` has no client caller |
| Comment threads cannot be edited or deleted | Only `POST /api/collaboration/comments/[id]/resolve` exists |
| Version history is capped and partly unreachable | `src/app/api/proposals/[id]/route.ts:38` uses `versions: { take: 20 }` with no list route; `GET,POST /api/documents/[id]/versions` has no client caller |
| Application views are not addressable | `/app` is a single route driven by the Zustand `view` field in `src/lib/store.ts:31-58` |
| Marketplace entries have no detail or lifecycle surface | Only `GET,POST /api/templates/marketplace` and `POST /api/templates/marketplace/[id]/use` exist |
| Five migrations are unapplied to the shared database | `prisma/migrations/20260724231500_*`, `20260725001000_*`, `20260725003000_*`, `20260725004000_*`, `20260725_phase4_proposal_system`; five route handlers carry `isPrismaMissingTable` fallbacks |

Three constraints apply to every requirement below and are treated as non-negotiable:

- **Real implementations only.** Every capability operates on persisted tenant data through executable code paths. Simulated data, hard-coded sample responses, and partial implementations are excluded. The single exception is a third-party service that is unavailable in the target environment; in that case real integration code sits behind a documented configuration boundary and the platform reports an explicit unavailable status.
- **Never pricing bids.** No requirement introduces a code path that calculates, suggests, recommends, or infers a commercial price, margin, discount, or bid amount.
- **Bilingual parity.** Every user-facing string, document, and error message is available in Arabic and English, and Arabic renders right-to-left.

## Glossary

- **Arabclue_Platform**: The complete Next.js application, including its route handlers, libraries, and user interface.
- **Account_Service**: The subsystem that creates user accounts, verifies email addresses, and performs credential recovery.
- **Invitation_Service**: The subsystem that grants a named email address membership of a workspace.
- **Analytics_Collector**: The subsystem that records `AnalyticsEvent` rows for workspace activity.
- **Analytics_API**: The route handler at `/api/analytics/proposals` that aggregates recorded analytics events.
- **Clause_Library**: The subsystem that stores, lists, and injects reusable bilingual contract clauses.
- **Contract_Template_Service**: The subsystem that stores workspace-authored contract templates and their immutable versions.
- **Structured_Export_Engine**: The subsystem in `src/lib/proposal-layout-export.ts` that renders a validated proposal snapshot to a delivery channel.
- **XLSX_Writer**: The component of the Structured_Export_Engine that produces spreadsheet output.
- **Recurring_Billing_Service**: The subsystem that creates, suspends, resumes, and cancels MyFatoorah recurring payment profiles.
- **Reconciliation_Service**: The subsystem that compares MyFatoorah payment state against local billing records.
- **Knowledge_Approval_Queue**: The subsystem that lists tenant knowledge records awaiting reviewer approval and records approval decisions.
- **Comment_Service**: The subsystem that stores, amends, resolves, and removes collaboration comments.
- **Presence_Service**: The subsystem that reports which users are viewing a proposal.
- **Version_History_API**: The route handlers that list, read, compare, and revert stored versions of a document or proposal.
- **App_Shell_Router**: The component that maps a browser URL to a Dashboard_View and maps a Dashboard_View to a browser URL.
- **Dashboard_View**: One member of the `DashboardView` union declared in `src/lib/store.ts`.
- **Marketplace_Service**: The subsystem that publishes, lists, reads, and retires template marketplace entries.
- **Localization_Registry**: The bilingual dictionary in `src/lib/i18n.ts` and the marketing dictionaries in `src/lib/marketing/`.
- **Schema_Guard**: The component that detects an absent database table at runtime and reports a migration-pending condition.
- **Validation_Gate**: The existing deterministic export gate in `src/lib/validation-gate.ts` and `src/lib/guardrails.ts`.
- **Tenant_Context**: The membership-scoped workspace resolution performed by `getTenantContext`.
- **Writer_Role**: A workspace member whose role permits mutation, as enforced by `requireWriter`.
- **Reviewer_Role**: A workspace member restricted to review decisions.
- **Configuration_Boundary**: A named environment variable set, documented in `.env.example` and `docs/`, that enables a third-party integration.
- **Unavailable_Status**: An HTTP 503 response carrying a stable machine-readable code, following the existing `PDF_UNAVAILABLE` pattern.

## Requirements

### Requirement 1: Self-Serve Account Creation

**User Story:** As a prospective customer who found Arabclue through the public pricing page, I want to create an account without contacting an administrator, so that I can evaluate the platform and purchase a plan.

#### Acceptance Criteria

1. WHEN a visitor submits a registration request containing an email address of 5 to 254 characters, a password of 10 to 128 characters, a display name whose trimmed length is 2 to 80 characters, and a workspace name whose trimmed length is 2 to 80 characters, THE Account_Service SHALL create one User record, one Workspace record, and one WorkspaceMember record granting the Writer_Role inside a single serializable database transaction that either commits all three records together or persists none of them, and SHALL return HTTP 201 with the code `REGISTRATION_CREATED` within 5 seconds of receiving the request.
2. IF a registration request supplies an email address whose trimmed, case-folded form already belongs to a User record, THEN THE Account_Service SHALL return HTTP 409 with the code `EMAIL_ALREADY_REGISTERED`, SHALL create no User, Workspace, or WorkspaceMember record, and SHALL leave every existing record unchanged.
3. IF a registration request supplies an email address that `src/lib/production-identities.ts` classifies as a reserved development identity blocked for the active runtime, THEN THE Account_Service SHALL return HTTP 400 with the code `RESERVED_IDENTITY`, SHALL evaluate this check before the uniqueness check stated in criterion 2, and SHALL create no User, Workspace, or WorkspaceMember record.
4. WHEN the Account_Service creates a User record through registration, THE Account_Service SHALL set the email verification state to unverified, SHALL generate exactly one single-use verification token that expires 24 hours after its stored creation timestamp, and SHALL exclude the raw token value from every API response and from log output.
5. WHILE a User record remains unverified, THE Arabclue_Platform SHALL admit that user's session only to the account-verification surface and the sign-out action, SHALL reject every other authenticated API request from that session with HTTP 403 and the code `EMAIL_VERIFICATION_REQUIRED`, and SHALL redirect every other authenticated page request from that session to the account-verification surface.
6. WHEN a visitor submits a valid, unexpired verification token, THE Account_Service SHALL mark the associated User record verified, SHALL invalidate that token against later submission, and SHALL return HTTP 200 with the code `EMAIL_VERIFIED`.
7. IF a visitor submits an expired, unknown, or already-consumed verification token, THEN THE Account_Service SHALL return HTTP 400 with the code `VERIFICATION_TOKEN_INVALID`, SHALL leave the verification state of every User record unchanged, and SHALL establish no session.
8. THE Account_Service SHALL rate limit registration requests to 5 per source address and SHALL rate limit verification-token submissions to 20 per source address, each counted over a rolling 60-minute window ending at the time of the incoming request.
9. WHERE the email Configuration_Boundary is unset, THE Account_Service SHALL commit the three records named in criterion 1, SHALL persist the verification token, SHALL return HTTP 202 with the code `VERIFICATION_EMAIL_UNCONFIGURED` excluding the raw token value, and SHALL append one audit log entry carrying the affected email address and a UTC timestamp.
10. THE Arabclue_Platform SHALL render every registration-form label, field hint, validation message, and error message named in this requirement from the Localization_Registry in Arabic with right-to-left direction and in English with left-to-right direction.
11. IF a registration request omits a required field, supplies a field whose trimmed length falls outside the bounds stated in criterion 1, or supplies an email address that fails email-address format validation, THEN THE Account_Service SHALL return HTTP 400 with the code `REGISTRATION_INVALID`, SHALL name every offending field in the response, and SHALL create no User, Workspace, or WorkspaceMember record.
12. IF a registration request or a verification-token submission exceeds a limit stated in criterion 8, THEN THE Account_Service SHALL return HTTP 429 with the code `REGISTRATION_RATE_LIMITED` for a registration request or `VERIFICATION_RATE_LIMITED` for a verification-token submission, SHALL create no User, Workspace, or WorkspaceMember record, and SHALL consume no verification token.
13. WHERE the email Configuration_Boundary is set, IF verification-email delivery returns a failure or does not complete within 30 seconds, THEN THE Account_Service SHALL retain the committed records and the persisted verification token, SHALL return HTTP 202 with the code `VERIFICATION_EMAIL_SEND_FAILED`, and SHALL append one audit log entry carrying the affected email address and a UTC timestamp.

### Requirement 2: Credential Recovery

**User Story:** As a user who forgot my password, I want to reset it myself, so that I regain access without an administrator resetting credentials manually.

#### Acceptance Criteria

1. WHERE the email Configuration_Boundary is set, WHEN a visitor submits a recovery request for an email address, THE Account_Service SHALL evaluate that address after trimming leading and trailing whitespace and converting it to lowercase, SHALL return HTTP 202 with the code `RECOVERY_REQUEST_ACCEPTED` and a response body identical for every submitted address of at most 254 characters regardless of whether that address matches a User record, and SHALL create no recovery token and send no recovery message unless the normalized address matches a User record that is marked active and whose email verification state is verified.
2. WHEN a recovery request matches a User record that is marked active and whose email verification state is verified, THE Account_Service SHALL create exactly one single-use recovery token bound to that User record, SHALL set that token to expire 60 minutes after creation, and SHALL invalidate every earlier unconsumed recovery token for that User record.
3. WHEN a visitor submits a valid, unexpired, unconsumed recovery token together with a new password of at least 10 and at most 128 characters, THE Account_Service SHALL replace the stored password hash, SHALL consume that token, SHALL revoke every UserSession row for that User record, and SHALL append a `PASSWORD_RESET` audit entry inside a single serializable database transaction, and SHALL return HTTP 200 with the code `PASSWORD_RESET_COMPLETE`.
4. IF a visitor submits an expired, unknown, or already-consumed recovery token, THEN THE Account_Service SHALL return HTTP 400 with the code `RECOVERY_TOKEN_INVALID`, SHALL leave the stored password hash unchanged, and SHALL leave every UserSession row for the associated User record unchanged.
5. THE Account_Service SHALL store recovery tokens as salted hashes, SHALL exclude raw token values from log output, audit entries, and API responses, and SHALL transmit a raw token value only in the recovery message sent to the matched User record's email address in that User record's persisted locale.
6. THE Account_Service SHALL limit recovery requests to at most 5 per normalized email address per rolling 60-minute window and SHALL limit recovery-token submissions to at most 20 per source address per rolling 60-minute window.
7. WHERE the email Configuration_Boundary is unset, THE Account_Service SHALL return HTTP 202 with the code `RECOVERY_EMAIL_UNCONFIGURED` for every recovery request regardless of whether the submitted address matches a User record, SHALL persist the recovery token created for a matched User record, and SHALL append an audit entry naming the affected email address.
8. IF a recovery request exceeds 5 submissions for the same normalized email address within a rolling 60-minute window, or a recovery-token submission exceeds 20 submissions from the same source address within a rolling 60-minute window, THEN THE Account_Service SHALL return HTTP 429 with the code `RECOVERY_RATE_LIMITED`, SHALL create no recovery token, and SHALL leave the stored password hash unchanged.
9. IF a visitor submits a valid, unexpired, unconsumed recovery token together with a new password shorter than 10 characters or longer than 128 characters, THEN THE Account_Service SHALL return HTTP 400 with the code `RECOVERY_PASSWORD_REJECTED`, SHALL leave that token unconsumed and valid until its stated expiry, and SHALL leave the stored password hash and every UserSession row unchanged.
10. THE Arabclue_Platform SHALL present the recovery request form and the new-password form in Arabic with right-to-left direction and in English with left-to-right direction, with every label, validation message, and confirmation drawn from the Localization_Registry.

### Requirement 3: Workspace Invitations

**User Story:** As a workspace owner, I want to invite a colleague who has no Arabclue account, so that my whole bid team can collaborate without each member registering separately.

#### Acceptance Criteria

1. WHEN a workspace owner or administrator submits an invitation containing an email address and a target role of administrator or member, THE Invitation_Service SHALL create one pending invitation record bound to the workspace resolved by Tenant_Context, the email address normalised to lower case, the target role, and a single-use token with an expiry of 7 days, SHALL create that record whether or not a User record already exists for that email address, SHALL invalidate every earlier unconsumed invitation for the same email address and workspace, and SHALL store the token as a salted hash that appears in no API response and no log entry.
2. WHILE no User record matches the invited email address, WHEN the invitee submits a valid, unexpired invitation token together with a display name of 2 to 120 characters and a password of at least 10 characters, THE Invitation_Service SHALL create the User record in a verified state, SHALL create the WorkspaceMember record with the invited role, SHALL consume the invitation token in a single serializable transaction that re-checks the absence of that User record, and SHALL return the workspace identifier and the granted role.
3. WHILE a User record matches the invited email address, WHEN the authenticated session of that same email address submits a valid, unexpired invitation token, THE Invitation_Service SHALL create the WorkspaceMember record with the invited role and SHALL consume the invitation token in a single serializable transaction.
4. IF an invitee already holds membership of the target workspace, THEN THE Invitation_Service SHALL return HTTP 409 with the code `ALREADY_A_MEMBER`, SHALL consume the invitation token, and SHALL leave the existing WorkspaceMember role unchanged.
5. IF a workspace member without owner or administrator role submits an invitation, THEN THE Invitation_Service SHALL return HTTP 403 with the code `INVITE_FORBIDDEN` and SHALL create no invitation record.
6. WHEN a workspace owner or administrator revokes a pending invitation of the workspace resolved by Tenant_Context, THE Invitation_Service SHALL mark that invitation consumed, SHALL exclude it from every later pending-invitation list, SHALL leave every WorkspaceMember row unchanged, and SHALL reject later submissions of its token with HTTP 400 and the code `INVITATION_REVOKED`.
7. WHEN a workspace owner or administrator requests the pending invitation list, THE Invitation_Service SHALL return the pending unexpired invitations of the workspace resolved by Tenant_Context in descending creation order with a bounded page size of at most 50 rows, each carrying the invited email address, role, inviter, creation timestamp, expiry timestamp, and email delivery state, and SHALL exclude consumed invitations, revoked invitations, and raw token values.
8. WHERE the active SubscriptionPlan defines a bounded seat allowance, IF the count of WorkspaceMember rows plus the count of pending unexpired invitations for the target workspace is not less than that allowance, THEN THE Invitation_Service SHALL return HTTP 429 with the code `SEAT_LIMIT_REACHED`, SHALL create no invitation record, and SHALL create no WorkspaceMember record.
9. IF an invitee submits an invitation token that is unknown, expired, or already consumed, THEN THE Invitation_Service SHALL return HTTP 400 with the code `INVITATION_TOKEN_INVALID`, SHALL create no User record, and SHALL create no WorkspaceMember record.
10. IF an authenticated session whose email address differs from the invited email address submits an invitation token, THEN THE Invitation_Service SHALL return HTTP 403 with the code `INVITATION_EMAIL_MISMATCH`, SHALL leave that invitation pending, and SHALL create no WorkspaceMember record.
11. IF an invitation acceptance supplies a display name outside 2 to 120 characters, a password shorter than 10 characters, or an email address matching a reserved development identity listed in `src/lib/production-identities.ts`, THEN THE Invitation_Service SHALL return HTTP 400 with a stable machine-readable code naming the rejected condition and an Arabic and English message, SHALL leave that invitation pending, and SHALL create no User record.

### Requirement 4: Activity Analytics Collection

**User Story:** As a bid manager, I want the analytics view to show my workspace's real proposal activity, so that I can report throughput and cycle time to my leadership.

#### Acceptance Criteria

1. WHEN a proposal is created, edited, submitted for review, approved, rejected, or exported, THE Analytics_Collector SHALL append exactly one AnalyticsEvent row per committed mutation, carrying the workspace identifier, one event type drawn from the closed event-type vocabulary, the entity type, the subject identifier, the actor identifier, and a UTC timestamp, and SHALL coalesce no two committed mutations into one row.
2. WHEN an agent run reaches a start, completion, failure, or cancellation transition, THE Analytics_Collector SHALL append exactly one AnalyticsEvent row carrying the workspace identifier, the run identifier, the transition drawn from the closed event-type vocabulary, and, for a completion, failure, or cancellation transition, the elapsed time from the recorded start transition as a non-negative whole number of milliseconds.
3. WHEN a document is uploaded or a document version is created, THE Analytics_Collector SHALL append exactly one AnalyticsEvent row carrying the workspace identifier, the document identifier, the actor identifier, one event type drawn from the closed event-type vocabulary, and the version identifier for a version-creation event.
4. IF appending an AnalyticsEvent row fails, THEN THE Analytics_Collector SHALL persist no partial row, SHALL make no further append attempt for that event, SHALL record the failure in the server log, SHALL leave every record written by the originating operation persisted, and SHALL return the originating operation's own response status and payload unchanged.
5. THE Analytics_Collector SHALL take the workspace identifier of every AnalyticsEvent row from Tenant_Context for a request-scoped operation and from the subject record's stored workspace for a background operation, SHALL take the actor identifier for a background operation from the member recorded as the initiator of the subject record, and SHALL append no row where neither source resolves exactly one workspace.
6. THE Analytics_Collector SHALL limit every AnalyticsEvent payload to identifiers, closed-vocabulary type values, counts, and durations, and SHALL exclude monetary amounts, price fields, bid values, and document body text from every AnalyticsEvent row.
7. WHEN the Analytics_API receives a request for a date range of at most 366 days, THE Analytics_API SHALL compute every returned figure only from AnalyticsEvent rows whose workspace identifier equals the caller's Tenant_Context workspace, and SHALL return the count of each vocabulary event type inside the range, the median elapsed time in whole milliseconds between each subject's earliest start-type event and its earliest matching terminal-type event inside the range, and the difference of each count against the immediately preceding range of equal length.
8. IF the requested range contains no AnalyticsEvent rows for the caller's workspace, THEN THE Analytics_API SHALL return HTTP 200 with every count set to zero, every difference set to zero, every median reported as unavailable rather than zero, and an explicit empty-range indicator set true.
9. THE Arabclue_Platform SHALL render every analytics metric label, axis label, legend entry, measurement unit, and empty-range message from the Localization_Registry with one non-empty Arabic string and one non-empty English string.
10. THE Arabclue_Platform SHALL maintain one closed event-type vocabulary shared by the Analytics_Collector and the Analytics_API, SHALL reject an append whose event type falls outside that vocabulary, and SHALL expose no Analytics_API metric whose event type no Analytics_Collector code path writes.
11. IF a request to the Analytics_API omits a range boundary, carries an unparseable boundary, places the start after the end, or spans more than 366 days, THEN THE Analytics_API SHALL return HTTP 400 with a stable machine-readable code identifying the invalid boundary and SHALL compute no metric.
12. WHEN an originating operation returns a success response, THE Analytics_Collector SHALL make the corresponding AnalyticsEvent row queryable by the Analytics_API within 5 seconds of that response.

### Requirement 5: Standard Clause Library

**User Story:** As a contract author, I want to browse and insert approved bilingual clauses, so that my draft covers the required articles without me retyping them.

#### Acceptance Criteria

1. THE Clause_Library SHALL persist one StandardClause row for every clause identifier exported by the frozen catalog in `src/lib/document-templates/contract-templates.ts`, each row carrying the clause identifier, category, Arabic title, English title, Arabic text, English text, mandatory flag, catalog order index, canonical hash recomputed from that catalog clause definition, an active flag set true, legal-review status `UNREVIEWED`, and a counsel-review-required flag set true.
2. WHEN clause seeding runs, THE Clause_Library SHALL leave a stored catalog row whose canonical hash equals the recomputed catalog hash unchanged in every field, SHALL create no additional row for a clause identifier that already exists, and SHALL leave every workspace-scoped custom clause unchanged.
3. WHEN a caller requests the clause list with an optional category filter and an optional mandatory filter, THE Clause_Library SHALL return the matching active clauses in ascending catalog order index, at most 50 rows per page with a deterministic cursor for the next page, each row carrying the clause identifier, category, Arabic text, English text, mandatory flag, and legal-review status.
4. WHEN a Writer_Role member selects at most 100 clause identifiers for a contract draft of a chosen catalog template family, THE Clause_Library SHALL return the selected active clauses in ascending catalog order index and SHALL add every clause whose identifier appears in that template family's catalog sections and whose mandatory flag is true.
5. IF a caller requests a clause identifier that is absent from the StandardClause table, inactive, or bound to a workspace other than the workspace resolved by Tenant_Context, THEN THE Clause_Library SHALL return HTTP 404 with the code `CLAUSE_NOT_FOUND` and SHALL return no clause text.
6. WHEN a Writer_Role member creates a workspace-scoped custom clause whose Arabic text and English text are each non-empty after trimming, THE Clause_Library SHALL store the clause bound to the workspace resolved by Tenant_Context with both texts exactly as submitted after trimming, legal-review status `UNREVIEWED`, and a counsel-review-required flag set true, and SHALL derive no monetary value from either text.
7. IF a custom clause submission omits either language text or supplies a language text that is empty after trimming, THEN THE Clause_Library SHALL return HTTP 400 with the code `CLAUSE_TRANSLATION_MISSING` naming the affected language and SHALL store no clause row.
8. IF submitted clause text contains HTML or XML tag syntax, unresolved template token syntax, or a Unicode bidirectional override or isolate control character, THEN THE Clause_Library SHALL return HTTP 400 with the code `UNSAFE_CLAUSE_TEXT` and SHALL store no clause row.
9. THE Arabclue_Platform SHALL present a clause browser that filters the list by category, marks every clause whose mandatory flag is true, displays the Arabic text right-to-left alongside the English text, displays the legal-review status and the counsel-review-required marker in Arabic and English, and inserts a selected clause into the active contract draft retaining both language texts.
10. THE Clause_Library SHALL restrict every custom clause read and write to the workspace resolved by Tenant_Context and SHALL expose every active catalog clause to every workspace.
11. THE Clause_Library SHALL set the mandatory flag true for a catalog clause whose declared applicability is `GENERAL` and false for a catalog clause whose declared applicability is `TENDER_SPECIFIC` or `COUNSEL_DECISION`.
12. IF clause seeding finds a stored catalog row whose canonical hash differs from the hash recomputed from the frozen catalog, THEN THE Clause_Library SHALL replace that row's category, titles, both language texts, mandatory flag, and canonical hash with the catalog values, SHALL increment that row's version, SHALL reset its legal-review status to `UNREVIEWED` with the counsel-review-required flag set true, and SHALL leave every workspace-scoped custom clause unchanged.
13. IF a clause request carries Arabic or English text longer than 20,000 characters after trimming, a category outside the category set declared by the frozen catalog, or more than 100 selected clause identifiers, THEN THE Clause_Library SHALL return HTTP 400 with the code `CLAUSE_FIELD_INVALID` naming the offending field path and SHALL store no clause row.

### Requirement 6: Contract Template Authoring and Versioning

**User Story:** As a bid manager, I want to author and version my own contract templates, so that my organisation's standard articles are reusable without a code change.

#### Acceptance Criteria

1. WHEN a Writer_Role member creates a workspace template containing a key of 3 to 64 characters, a non-empty Arabic title and a non-empty English title of at most 200 characters each, 1 to 100 ordered sections that each carry non-empty Arabic text and non-empty English text of at most 20,000 characters per language, and at most 100 variable definitions, THE Contract_Template_Service SHALL store one ContractTemplate row and one immutable ContractTemplateVersion row whose version identifier equals 1 and whose canonical hash is computed from the stored sections, variable definitions, and clause bindings, inside a single serializable database transaction, and SHALL return the persisted version identifier and canonical hash.
2. WHEN a Writer_Role member updates a stored workspace template, THE Contract_Template_Service SHALL apply, inside a single serializable database transaction, an idempotent version operation that creates one ContractTemplateVersion row whose version identifier equals the current version identifier plus 1 and advances the template's current version pointer to that identifier for submitted content whose canonical hash differs from the current version, creates no row and returns the current version identifier for submitted content whose canonical hash equals the current version, and leaves every earlier ContractTemplateVersion row unmodified in both cases.
3. WHEN a caller requests the version list of a workspace template, THE Contract_Template_Service SHALL return the stored versions in descending version-identifier order with keyset pagination, a bounded page size of at most 50 rows, a cursor for the next page, and, for each version, its version identifier, canonical hash, author identifier, creation timestamp in UTC, and current-version indicator.
4. WHEN a caller requests one template version by its version identifier, THE Contract_Template_Service SHALL return the ordered sections with their Arabic text and English text, the variable definitions with their declared types, and the clause bindings exactly as persisted for that version together with the stored canonical hash, and SHALL exclude content persisted by any other version.
5. IF a template submission declares a variable that no section references, THEN THE Contract_Template_Service SHALL return HTTP 400 with the code `UNREFERENCED_TEMPLATE_VARIABLE` and the offending variable name, SHALL create no ContractTemplateVersion row, and SHALL leave every stored version unchanged.
6. IF a template section references a variable that the submission does not declare, THEN THE Contract_Template_Service SHALL return HTTP 400 with the code `UNDECLARED_TEMPLATE_VARIABLE` and the offending token, SHALL create no ContractTemplateVersion row, and SHALL leave every stored version unchanged.
7. THE Contract_Template_Service SHALL store every workspace template and every one of its ContractTemplateVersion rows with legal-review status `UNREVIEWED`, a counsel-review-required flag set true, and a non-executable flag set true, and SHALL derive those three values internally rather than from caller-supplied input.
8. WHEN a Writer_Role member deletes a workspace template, THE Contract_Template_Service SHALL mark the template retired, SHALL retain every ContractTemplateVersion row of that template and every GeneratedContract row that references any of those versions, SHALL keep every retained version readable by its version identifier, and SHALL exclude the retired template from template selection lists and from new contract generation.
9. IF a template submission supplies a key that matches a key in the frozen contract template catalog, THEN THE Contract_Template_Service SHALL return HTTP 409 with the code `RESERVED_TEMPLATE_KEY` and the colliding key, and SHALL store no ContractTemplate row and no ContractTemplateVersion row.
10. WHEN a Writer_Role member opens the template editor, THE Arabclue_Platform SHALL present controls that edit each section's Arabic text with right-to-left direction and English text with left-to-right direction, declare each variable with a type of text, number, date, or single-choice list, bind clauses from the Clause_Library, and refresh the preview rendered by the existing preview route within 3 seconds of an accepted edit.
11. THE Contract_Template_Service SHALL restrict every workspace template read and write to the workspace resolved by Tenant_Context and SHALL return HTTP 404 with the code `TEMPLATE_NOT_FOUND` for a template identifier or version identifier absent from that workspace without mutating any stored row.
12. IF a template submission omits the Arabic text or the English text of the title or of any section, or violates the stated bound on key length, section count, section text length, or variable count, THEN THE Contract_Template_Service SHALL return HTTP 400 with the code `TEMPLATE_SUBMISSION_INVALID` and the offending field path, and SHALL create no ContractTemplate row and no ContractTemplateVersion row.
13. IF a create submission supplies a key already stored by a ContractTemplate row in the workspace resolved by Tenant_Context, THEN THE Contract_Template_Service SHALL return HTTP 409 with the code `TEMPLATE_KEY_IN_USE`, SHALL create no ContractTemplateVersion row, and SHALL leave the existing template and its versions unchanged.
14. IF two concurrent update requests for one workspace template resolve to the same next version identifier, THEN THE Contract_Template_Service SHALL persist exactly one ContractTemplateVersion row for that identifier and SHALL return HTTP 409 with the code `TEMPLATE_VERSION_CONFLICT` and the current version identifier to the request that persisted no row.

### Requirement 7: Contract Instance Version History

**User Story:** As a reviewer, I want to see how a generated contract changed between revisions, so that I can approve a specific frozen state with confidence.

#### Acceptance Criteria

1. WHEN a GeneratedContract row is created, or its variable values or selected clauses are amended such that its recomputed canonical hash differs from the canonical hash of the highest revision already stored for that contract, THE Contract_Template_Service SHALL store, inside the same database transaction as that contract mutation, one contract version row that no later operation updates or deletes, carrying the next revision number for that contract counting from 1 and increasing by exactly 1 per stored version, the variable values, the selected clause identifiers, the referenced template version, the rendered bilingual document specification, the author identifier, the creation timestamp, and the canonical hash computed over those stored values.
2. 9. IF a caller requests a marketplace entry identifier that does not exist, THEN THE Marketplace_Service SHALL return an error indicating that no marketplace entry matches the identifier and SHALL return no partial entry fields.
10. IF a rate request supplies a value that is not an integer from 1 through 5, THEN THE Marketplace_Service SHALL reject the request with an error indicating the rating value is outside the permitted range and SHALL leave the entry stored ratings and average rating unchanged.
11. IF a retire request targets an entry published by a workspace other than the workspace resolved by Tenant_Context, THEN THE Marketplace_Service SHALL reject the request with an error indicating the caller is not the publisher and SHALL keep the entry present in list results.

### Requirement 16: Schema Migration Readiness

**User Story:** As a release engineer, I want unapplied schema changes to be visible and safely handled at runtime, so that a deployment never appears healthy while a feature silently cannot store data.

#### Acceptance Criteria

1. THE Arabclue_Platform SHALL express every schema change introduced by this specification as an additive migration file under `prisma/migrations` that adds only tables, columns, indexes, or constraints, that contains no statement dropping or renaming an existing table or column and no statement narrowing an existing column type, and in which every added column is nullable or carries a default value so that the migration applies to a table already holding rows.
2. IF a route handler reaches a database table that the connected database does not contain, THEN THE Schema_Guard SHALL return an Unavailable_Status carrying the code `SCHEMA_MIGRATION_PENDING`, the missing table name, an Arabic message, and an English message, SHALL persist no part of the attempted write, and SHALL issue no statement that creates or alters that table.
3. WHEN the readiness endpoint runs, THE Arabclue_Platform SHALL compare every migration present under `prisma/migrations` against the applied-migration record of the connected database, SHALL report the identifier of every migration that record does not list as applied without truncating the list, SHALL return that report separately from the existing liveness result, SHALL complete within 5 seconds, and SHALL issue no schema-mutating statement.
4. WHILE one or more migrations under `prisma/migrations` remain absent from the applied-migration record, THE Arabclue_Platform SHALL report a not-ready readiness state carrying the code `SCHEMA_MIGRATION_PENDING`, every unapplied migration identifier, and the capability names each unapplied migration affects, and SHALL report no ready state until every migration is listed as applied.
5. THE Arabclue_Platform SHALL exclude every schema-mutating command, including migration apply, migration development, schema push, and reset commands, from the build script, the development script, and the start script, and SHALL restrict those three scripts to commands that issue no data-definition statement against the connected database.
6. THE Arabclue_Platform SHALL document every migration introduced by this specification, including the five migrations `20260724231500_*`, `20260725001000_*`, `20260725003000_*`, `20260725004000_*`, and `20260725_phase4_proposal_system`, in the production deployment runbook with its migration identifier, the capability names it affects, its ordered position in the apply sequence, and either its reverse action or an explicit statement that it has no reverse action.
7. THE Arabclue_Platform SHALL route every missing-table condition raised by a route handler through the Schema_Guard and SHALL exclude every fallback that returns a success status carrying an empty or synthesized result in place of the missing table's data.
8. IF the readiness check cannot reach the connected database, cannot read the applied-migration record, or does not complete within 5 seconds, THEN THE Arabclue_Platform SHALL report a not-ready readiness state carrying a stable machine-readable code that names the failure condition and SHALL report no ready state.
9. IF the build script, the development script, or the start script contains a schema-mutating command, THEN THE Arabclue_Platform SHALL fail the deployment safety check and SHALL name the offending script in the failure output.

### Requirement 17: Transactional Notification Delivery

**User Story:** As a workspace member, I want to be emailed when something needs my attention, so that a review or a payment problem does not stall for days.

#### Acceptance Criteria

1. WHEN a proposal is submitted for review, THE Arabclue_Platform SHALL send one notification to each reviewer assigned to the approval policy step that is active immediately after that submission, in that reviewer's persisted locale, for at most 50 recipients per submission.
2. WHEN a review decision is recorded, THE Arabclue_Platform SHALL send one notification to the proposal author in the author's persisted locale, carrying the localized decision outcome and the deciding reviewer's display name.
3. WHEN a Subscription status transitions from any other status to past due or failed, THE Arabclue_Platform SHALL send one notification to each workspace owner and administrator holding active membership, in that recipient's persisted locale, for at most 50 recipients per transition.
4. WHEN the database transaction that records a triggering event commits, THE Arabclue_Platform SHALL create one in-application Notification record per recipient, SHALL create one delivery row keyed on the event identifier and the recipient identifier under a uniqueness constraint, SHALL request exactly one provider message for that delivery row within 60 seconds of that commit, and SHALL request no further provider message for an event-and-recipient pair whose delivery row already records a successful delivery.
5. IF a provider delivery request returns an error or does not complete within 10 seconds, THEN THE Arabclue_Platform SHALL record the failure with the event identifier, the recipient identifier, and the attempt number, SHALL retain the in-application Notification record, SHALL allow the triggering operation to complete, SHALL make at most 3 delivery attempts for that delivery row within 30 minutes of the first attempt, and SHALL set the delivery row state to failed after the third unsuccessful attempt.
6. WHERE the email Configuration_Boundary is unset, THE Arabclue_Platform SHALL create the in-application Notification record, SHALL record an unconfigured-provider entry carrying the code `NOTIFICATION_EMAIL_UNCONFIGURED` with the event identifier and the recipient identifier, SHALL request no provider message, and SHALL allow the triggering operation to complete.
7. THE Arabclue_Platform SHALL limit every notification body to the localized event label, the subject title, the actor display name, the event timestamp in UTC, and exactly one link to the Dashboard_View path of the referenced record, SHALL limit the subject line to at most 150 characters, and SHALL exclude monetary amounts, bid values, document body text, and file attachments.
8. THE Arabclue_Platform SHALL compose every notification subject and body from Localization_Registry entries that carry a non-empty Arabic string and a non-empty English string, SHALL select the recipient's persisted locale, and SHALL select Arabic when the recipient has no persisted locale.
9. IF the database transaction that records a triggering event does not commit, THEN THE Arabclue_Platform SHALL create no in-application Notification record and SHALL request no provider message for that event.
10. IF a triggering event resolves to no eligible recipient, THEN THE Arabclue_Platform SHALL record a no-recipient entry naming the event identifier and the absent recipient role, SHALL request no provider message, and SHALL allow the triggering operation to complete.
11. WHILE the recipient's resolved locale is Arabic, THE Arabclue_Platform SHALL set right-to-left direction and Arabic language on the notification subject and body.

### Requirement 18: Bilingual and Right-to-Left Completeness

**User Story:** As an Arabic-speaking bid manager, I want every screen and message in correct Arabic with right-to-left layout, so that I never have to fall back to English to understand the platform.

#### Acceptance Criteria

1. THE Localization_Registry SHALL contain, for every registered key, one Arabic value and one English value that each contain at least one non-whitespace character and that each declare an identical set of named interpolation placeholders, and SHALL contain at least one Arabic-script character in the Arabic value of every key whose value is narrative text rather than a shared identifier, numeral, or retained Latin-script technical term.
2. THE Localization_Registry SHALL contain an entry for every key referenced by a translation lookup in the application source, including every key that a composed or dynamically selected lookup can produce.
3. WHILE the persisted locale preference is Arabic, or while no locale preference is stored, THE Arabclue_Platform SHALL set the document direction to right-to-left and the document language to Arabic in the markup initially served for every public page, every Dashboard_View, and every dialog, and SHALL present no rendered frame in left-to-right direction.
4. WHEN the Arabclue_Platform returns a client-visible error, THE Arabclue_Platform SHALL include a stable machine-readable code, an Arabic message, and an English message, each message containing at least one non-whitespace character and naming the action that failed.
5. THE Arabclue_Platform SHALL render every form label, help text, validation message, empty state, confirmation dialog, and notification text introduced by this specification exclusively from the Localization_Registry, with no user-facing literal string embedded in component or route-handler source.
6. THE Arabclue_Platform SHALL position every interface element introduced by this specification using logical inline properties rather than physical left or right properties, and SHALL render the Arabic layout as the horizontal mirror of the English layout at viewport widths of 360, 768, and 1280 CSS pixels, with no content extending horizontally beyond the viewport width and with each element's inline-start offset differing from its English counterpart by no more than 2 CSS pixels.
7. THE Arabclue_Platform SHALL exclude Arabic-script characters from English document output and SHALL exclude Latin-script narrative sentences from Arabic document output, SHALL retain in both outputs the shared identifiers, numerals, dates, units, and Latin-script technical terms present in the source record, and SHALL reproduce user-authored content exactly as the user entered it.
8. WHEN a user selects a locale through the language control, THE Arabclue_Platform SHALL apply that locale's document direction and document language within 1 second, SHALL persist the selection so that a page reload and a subsequent browser session restore the same locale, and SHALL keep the user on the Dashboard_View that was active before the selection.
9. IF a translation lookup or a client-visible error resolves to no value for the active locale, THEN THE Arabclue_Platform SHALL render the value stored for the other locale when one exists, SHALL otherwise render the requested key identifier, SHALL render neither an empty string nor a runtime failure to the user, and SHALL record the missing-translation condition together with the requested key and locale.
10. IF a document section required for the requested output language has no value for that language in the Localization_Registry, THEN THE Arabclue_Platform SHALL block the export through the Validation_Gate, SHALL return an error identifying the affected section and the missing language, and SHALL leave the stored proposal content unchanged.

### Requirement 19: Production Implementation Integrity

**User Story:** As the product owner, I want every capability in this specification backed by real working code, so that no screen presents invented data to a paying customer.

#### Acceptance Criteria

1. THE Arabclue_Platform SHALL derive every value displayed by a capability in this specification from a persisted database record scoped to the workspace resolved by Tenant_Context, a verified third-party response, or a deterministic computation over those inputs, and SHALL treat static interface text drawn from the Localization_Registry as the only exception.
2. WHERE a third-party service is required and its Configuration_Boundary is unset, THE Arabclue_Platform SHALL retain the real integration code path unchanged, SHALL return an Unavailable_Status carrying a stable machine-readable code that names the unset Configuration_Boundary, SHALL persist no record derived from a substitute value, and SHALL display no substitute value in place of the unavailable data.
3. THE Arabclue_Platform SHALL exclude hard-coded sample records, synthetic third-party response fixtures, stub functions that return a constant in place of a real operation, randomly generated display values, and artificial delays from every module reachable at runtime from a route handler, a page, or a layout, and SHALL confine such constructs to files under the test directory.
4. WHEN a form introduced by this specification is submitted, THE Arabclue_Platform SHALL validate the payload on the server against a declared schema covering field type, required-ness, and maximum length, SHALL persist the accepted result in a single transaction, and SHALL return the persisted state read back after that transaction commits.
5. THE Arabclue_Platform SHALL resolve Tenant_Context and enforce the caller's workspace role on every route handler introduced by this specification before reading or mutating any record, and SHALL reject a request that targets a record outside the resolved workspace with a not-found or forbidden result while mutating no record.
6. THE Arabclue_Platform SHALL apply the existing Validation_Gate to every export path introduced by this specification, SHALL block the export when pricing language, an unresolved placeholder, or an unverified regulatory identifier is present, SHALL return the stable machine-readable code of the failed check, and SHALL emit no output artifact for a blocked export.
7. THE Arabclue_Platform SHALL exclude every code path that calculates, suggests, recommends, or infers a bid price, margin, discount, unit rate, monetary total, or commercial strategy, and SHALL copy commercial values into any output exactly as the tenant stored them.
8. THE Arabclue_Platform SHALL pass `bun run lint`, `bunx tsc --noEmit`, `bun run test`, and `bun run build` with zero reported errors and zero failing tests while every capability in this specification is present.
9. IF a payload submitted to a capability introduced by this specification fails server-side schema validation, THEN THE Arabclue_Platform SHALL reject the submission with a stable machine-readable code naming the offending field path, SHALL persist no part of that payload, and SHALL return an Arabic message and an English message.
10. THE Arabclue_Platform SHALL exclude a not-implemented response, a not-supported response, and a coming-soon response from every capability introduced by this specification, and SHALL restrict Unavailable_Status responses to the unset Configuration_Boundary conditions and the pending-migration condition named in this specification.
11. THE Arabclue_Platform SHALL make every route handler and library function introduced by this specification reachable from at least one interface control, scheduled task, or documented external caller, and SHALL exclude any route handler introduced by this specification that no such caller invokes.
